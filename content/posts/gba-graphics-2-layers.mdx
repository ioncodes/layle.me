The *Shaman King* frame has 4 of them, though, plus the sprites that make up the player character. They all overlap. For every pixel, the GBA has to decide which of them ends up on screen. This part looks at how it makes that decision, where the sprites come from, how windows hide parts of a layer and how blending, fades and mosaic change the colors that end up on screen.

## Backgrounds and priority

In mode 0, the GBA has 4 tiled backgrounds, BG0 to BG3, each switched on by its own bit in `DISPCNT` and configured by its own `BGxCNT` register. Bits 0 and 1 of [`BGxCNT`](https://problemkaputt.de/gbatek-lcd-i-o-bg-control.htm) hold the background's priority, from 0 at the front to 3 at the back. Wherever a background has a transparent pixel, the next one shows through. Where none of them has anything to draw, the screen shows the backdrop color from palette entry 0.

Sprites, which get their own section below, have a priority as well. It's stored per sprite in OAM attribute 2 and uses the same 0 to 3 scale. The *Shaman King* frame from [Part 1](/posts/gba-graphics-1-tiles/) uses all 4 backgrounds and 2 sprites:

| Layer | Priority | Content |
| --- | ---: | --- |
| BG0 | 0 | Health bars and name |
| BG1 | 2 | Ground, cacti and the cliff |
| BG2 | 3 | Hills in the distance |
| BG3 | 3 | Sky and clouds |
| Sprites | 2 | The player character |

When 2 backgrounds have the same priority, the one with the lower BG number appears in front. BG2 and BG3 both have priority 3, so BG2's hills cover BG3's sky. Sprites appear in front of backgrounds with the same priority, which puts the player in front of the ground at priority 2. The health bars at priority 0 would still cover the player character if they overlapped.

Toggle the layers below or change their priorities. Giving BG3 priority 2, for example, puts the sky in front of the hills. The visible part of the sky has no transparent pixels, so the hills disappear completely. The hills also show how sprites interact with backgrounds, since the character stands in front of them. At priority 2, the hills tie with the sprites and the character stays in front. At priority 1, the hills move in front of both the ground and the character. Only the character's head is left against the sky. Setting the sprites to 1 as well brings the character back, because the tie goes to the sprites again.

<GbaLayerStack />

Sly renders each enabled background into a line of its own. To see how it picks an opaque pixel, we can simplify the compositor to a sorted list of backgrounds. Starting in order from BG0 to BG3, Rust's stable `sort_by_key` keeps that order for equal priorities:

```rust
bg_order.sort_by_key(|&(_, priority)| priority);
```

The sprites get a line of their own as well, where each pixel remembers a color and priority. In this simplified version, we take the first background that isn't transparent and compare its priority with the sprite's. The sprite wins if its number is the same or lower. Where no background has anything to draw, the backdrop stands in with a priority of `u8::MAX`, so a sprite always covers it. Blending also needs the next layer, which we'll get to later:

```rust
let (mut color, bg_priority) = bg_order
    .iter()
    .find_map(|&(index, priority)| bg_lines[index][x].map(|color| (color, priority)))
    .unwrap_or((backdrop, u8::MAX));

if let Some(sprite) = sprite_line[x]
    && sprite.priority <= bg_priority
{
    color = sprite.color;
}
```

## Sprites

Backgrounds fill the whole screen, but plenty of things in a game need to move around on their own: characters, cursors, projectiles and often text. The GBA draws these as **sprites**, also called [objects, or OBJs](https://problemkaputt.de/gbatek-lcd-obj-overview.htm). A sprite is a small image built from 8 × 8 tiles that the hardware draws at any position on the screen.

*Action Man: Robot Atak* uses both kinds of PPU modes in this series. Its island map is a mode 3 bitmap from [Part 1](/posts/gba-graphics-1-tiles/) with sprites on top, whereas its levels use the tiled backgrounds from [Part 1](/posts/gba-graphics-1-tiles/). Drag the slider to remove the backgrounds from a level: everything that's left is a sprite.

### Object attribute memory

Each sprite is described by an entry in **OAM**, the 1 KiB of object attribute memory at `0x07000000`. There's room for 128 entries, 8 bytes apart. Each one holds 3 16-bit attributes. The 4th halfword in each entry belongs to the rotation and scaling parameters, which [Part 3](/posts/gba-graphics-3-affine/) covers.

<BitLayout rows={[

    { bits: [0, 7], name: 'Y position' },
    { bits: [8, 9], name: 'Rotation, scaling and hiding' },
    { bits: [10, 12], name: 'Blending, windows and mosaic' },
    { bits: 13, name: '4 or 8 bits per pixel' },
    { bits: [14, 15], name: 'Shape: square, wide or tall' },
  ] },
  { label: 'Attribute 1', fields: [
    { bits: [0, 8], name: 'X position' },
    { bits: [9, 11], name: 'Unused unless rotated or scaled', unused: true },
    { bits: 12, name: 'Horizontal flip' },
    { bits: 13, name: 'Vertical flip' },
    { bits: [14, 15], name: 'Size' },
  ] },
  { label: 'Attribute 2', fields: [
    { bits: [0, 9], name: 'First tile number' },
    { bits: [10, 11], name: 'Priority relative to the backgrounds' },
    { bits: [12, 15], name: 'Palette bank' },
  ] },
]} />

Shape and size together pick 1 of 12 sizes, in pixels. Shape 3 isn't allowed:

| Size | Square | Wide | Tall |
| ---: | --- | --- | --- |
| 0 | 8 × 8 | 16 × 8 | 8 × 16 |
| 1 | 16 × 16 | 32 × 8 | 8 × 32 |
| 2 | 32 × 32 | 32 × 16 | 16 × 32 |
| 3 | 64 × 64 | 64 × 32 | 32 × 64 |

<FunFact>

The hardware only has so much time to draw sprites on each line. The GBA's [sprite drawing budget](https://problemkaputt.de/gbatek-lcd-obj-overview.htm) is 1'210 cycles per line, or 954 if bit 5 of `DISPCNT` frees up HBLANK for OAM access. A regular sprite costs 1 cycle per pixel of its width. With the larger budget, all 128 sprites fit if they're 8 pixels wide. At 64 pixels wide, 18 fit completely, leaving 58 cycles for part of another. Sprites off screen to the side can still use up the budget, so keeping the visible ones at the start of OAM helps them get drawn before time runs out.

</FunFact>

Larger shapes are often built from several sprites. Action Man himself is 6 sprites in 5 different sizes. The word "ADVENTURE" on the map is 9 separate 8 × 8 sprites placed 5 to 7 pixels apart, so the letters overlap where their tiles are blank. Both E's point at tile 515, because the image only has to be stored once.

The Y position only has 8 bits. The health bar is a 64 × 32 sprite at <Math tex="y = 247" />, so its rows continue past 255 and wrap around to the top of the screen. Subtracting on 8-bit values reproduces this wraparound:

```rust
for attr in sprite::attributes(memory.oam) {
    // ...
    let (width, height) = attr.dimensions();
    let row = (line as u8).wrapping_sub(attr.y_coordinate()) as usize;
    if row >= height {
        continue;
    }
    // ...
}
```

The X position has 9 bits and wraps the same way at 512, so a sprite at <Math tex="x = 500" /> starts 12 pixels left of the screen and shows only its right part. These rules cover the regular sprites here. Affine sprites with a 128-pixel-high double size area have a [Y wrapping exception](https://github.com/mgba-emu/mgba/issues/2824).

When 2 opaque sprite pixels overlap, the [lower priority number](https://github.com/mgba-emu/mgba/issues/2809) wins. If their priorities match, the lower OAM entry appears in front. Going through entries from 0 upwards, a later opaque pixel only replaces one with a higher priority number:

```rust
if dst.is_none_or(|pixel| attr.priority() < pixel.priority) {
```

### Tiles and palettes

A sprite's image comes from sprite tile memory, the 32 KiB of VRAM starting at `0x06010000`. Tile numbers count 32-byte units, so tile <Math tex="n" /> starts at <Math tex={String.raw`\texttt{0x06010000} + 32n`} />. The bitmap modes from [Part 1](/posts/gba-graphics-1-tiles/) take the first half of that area, so they only leave tiles 512 to 1023. That's why every sprite on *Action Man*'s mode 3 map uses a tile number of at least 512, whereas the level's sprites start at 0.

All the sprites in these frames use 4 bits per pixel, which fits 2 pixels into each byte and makes a tile exactly 32 bytes. Each 4-bit value selects 1 of 16 colors from the sprite's palette bank, 1 of 16 banks in the sprite palette at `0x05000200`. Value 0 is always transparent, which is how a 32 × 32 square becomes Action Man's round portrait.

A sprite can also use 8 bits per pixel and the whole 256-color sprite palette. Its tiles then take 64 bytes, but tile numbers still count in steps of 32 bytes, so [GBATEK](https://problemkaputt.de/gbatek-lcd-obj-oam-attributes.htm) notes that "only each second tile may be used, the lower bit of the tile number should be zero (in 2-dimensional mapping mode, the bit is completely ignored)".

### Finding the rest of the tiles

OAM only stores the first tile of a sprite, so the hardware needs a rule for where the others are. Bit 6 of `DISPCNT` selects one of 2 layouts:

- With **1D mapping**, a sprite's tiles simply follow each other in memory, row by row.
- With **2D mapping**, tile memory is treated as a grid 32 tiles wide, so the next row of a sprite starts 32 tile numbers later.

For a 4-bit sprite that's <Math tex="w" /> pixels wide, the tile at column <Math tex={String.raw`t_x`} /> and row <Math tex={String.raw`t_y`} /> is therefore:

<Math block tex={String.raw`\begin{aligned} \text{1D: } & n + t_y \cdot \frac{w}{8} + t_x \\[0.4em] \text{2D: } & n + 32\,t_y + t_x \end{aligned}`} />

With 8 bits per pixel, each tile takes 2 numbers, so the column offset doubles in both layouts. With 1D mapping, the row offset doubles as well. Both *Action Man* frames set bit 6 and use 1D mapping. Switch the demo to **2D mapping** to see what happens when the 2 disagree: single-row sprites like the letters are unaffected, while taller sprites read their lower rows from different addresses. The image changes wherever those addresses hold different tile data.

Priorities decide which layer ends up in front, but they can't hide part of a layer while showing the rest. That's what windows are for. *Tales of Phantasia* opens with a quote that appears from left to right, one line after the other. ### Rectangles

A [window](https://problemkaputt.de/gbatek-lcd-i-o-window-feature.htm) is a region of the screen with its own list of visible layers. The GBA has 2 rectangular windows, window 0 and window 1, which bits 13 and 14 of `DISPCNT` switch on. 2 registers set the edges of each one: `WINxH` holds the left and right edge, while `WINxV` holds the top and bottom.

<BitLayout rows={[

  ] },
  { label: 'WIN0V and WIN1V', fields: [
    { bits: [0, 7], name: 'Y2, bottom edge plus 1' },
    { bits: [8, 15], name: 'Y1, top edge' },
  ] },
]} />

In the frame above, `WIN0H` is `0x71e8` and `WIN0V` is `0x3047`. Window 0 therefore covers x 113 to 231 and y 48 to 70, which is the part of the first line that hasn't appeared yet:

<GbaWindowDiagram x1={113} x2={232} y1={48} y2={71} caption="X2 and Y2 are the first column and row past the window, so it ends at 231 and 70." />

Window 1 covers the lines below it, from y 72 to 110. Every frame, the game moves window 0's left edge up to 2 pixels to the right. Once the first line is complete, both windows move down to the next one.

### What each region shows

`WININ` and `WINOUT` decide which layers each region lets through. They hold a byte per region, with a bit for each background, one for the sprites and one for the color special effects, such as blending:

<BitLayout rows={[
  { label: 'WININ', fields: [
    { bits: [0, 3], name: 'Window 0: BG0-BG3' },
    { bits: 4, name: 'Window 0: sprites' },
    { bits: 5, name: 'Window 0: effects' },
    { bits: [8, 11], name: 'Window 1: BG0-BG3' },
    { bits: 12, name: 'Window 1: sprites' },
    { bits: 13, name: 'Window 1: effects' },
  ] },
  { label: 'WINOUT', fields: [
    { bits: [0, 3], name: 'Outside: BG0-BG3' },
    { bits: 4, name: 'Outside: sprites' },
    { bits: 5, name: 'Outside: effects' },
    { bits: [8, 11], name: 'OBJ window: BG0-BG3' },
    { bits: 12, name: 'OBJ window: sprites' },
    { bits: 13, name: 'OBJ window: effects' },
  ] },
]} />

The intro sets `WININ` to `0x0000` and `WINOUT` to `0x000f`, so nothing is visible inside either window, whereas all 4 backgrounds are visible outside them. A layer still has to be switched on in `DISPCNT` as well, so only BG3 actually appears. Wherever a window hides everything, the screen shows the backdrop color, which is black here.

A pixel can be inside several windows at once. The GBA checks window 0 first, then window 1 and then the OBJ window. Every other pixel counts as outside. In the demo below, show BG3 in window 1 to bring back the rest of the quote, or drag window 1 up over window 0. Where they overlap, window 0's setting wins:

### Sprite-shaped windows

The third window has no rectangle at all. A sprite whose mode in attribute 0 is set to OBJ window isn't drawn. Instead, every pixel of it that isn't transparent becomes part of the OBJ window. Both bit 12 of `DISPCNT`, for sprite processing, and bit 15, for the OBJ window, must be on. That way, a window can take any shape a sprite can. The high byte of `WINOUT` decides what's visible inside it.

The window checks follow that same order:

```rust
if let Some(index) = (0..2).find(|&index| windows.contains(index, x, y)) {
    return Some(WindowRegion::Rectangle(index));
}

Some(if windows.obj_enabled && inside_obj_window {
    WindowRegion::Obj
} else {
    WindowRegion::Outside
})
```

The region picks a byte of `WININ` or `WINOUT`. A layer whose bit in that byte is clear is hidden in that region.

### First and second targets

`BLDCNT` decides which layers take part and what happens to them:

<BitLayout label="BLDCNT" fields={[
  { bits: [0, 5], name: 'First targets: BG0-BG3, sprites, backdrop' },
  { bits: [6, 7], name: 'Effect' },
  { bits: [8, 13], name: 'Second targets: BG0-BG3, sprites, backdrop' },
]} />

The effect is 0 for none, 1 for alpha blending, 2 to brighten and 3 to darken. Alpha blending only happens where the frontmost pixel belongs to a first target and the pixel right behind it to a second target. Everywhere else, the top pixel is shown as it is. *Golden Sun* sets `BLDCNT` to `0x3f42`: BG1 is the only first target, the effect is 1 and every layer is a second target, so wherever BG1 is the frontmost visible layer, it's mixed with whatever is behind it.

### Mixing the colors

`BLDALPHA` holds 2 weights in sixteenths: **EVA** for the first target in bits 0 to 4 and **EVB** for the second target in bits 8 to 12. Each color channel is mixed on its own:

<Math block tex={String.raw`I = \min\left(31,\ \left\lfloor\frac{I_1 \cdot \text{EVA} + I_2 \cdot \text{EVB}}{16}\right\rfloor\right)`} />

<Math tex="I_1" /> is the channel of the first target and <Math tex="I_2" /> the one behind it, both from 0 to 31. EVA and EVB have 5 bits each, but the GBA treats any value from 17 to 31 as 16. *Golden Sun*'s `BLDALPHA` of `0x1006` means EVA = 6 and EVB = 16, so the room keeps its full strength and 6/16 of the light is added on top. The pixel at (225, 82) has BG1 = (14, 16, 1) in front of BG3 = (14, 13, 0):

<Math block tex={String.raw`\begin{aligned} \text{red} &= \frac{14 \cdot 6 + 14 \cdot 16}{16} \\ &= \frac{308}{16} = 19.25 \\[0.4em] \text{green} &= \frac{16 \cdot 6 + 13 \cdot 16}{16} \\ &= \frac{304}{16} = 19 \\[0.4em] \text{blue} &= \frac{1 \cdot 6 + 0 \cdot 16}{16} \\ &= \frac{6}{16} = 0.375 \end{aligned}`} />

The hardware drops the fraction, which gives (19, 19, 0). The 2 weights add up to more than 16 here, so a bright light on a bright part of the room can go past 31. That's what the minimum is for. In the demo below, 409 visible BG1 pixels need at least one channel capped at 31. Change the weights or click a pixel to see its calculation:

<GbaBlend />

The formula translates directly into code:

```rust
(((top_channels[i] * self.eva) + (below_channels[i] * self.evb)) >> 4).min(31)
```

Sprites have a shortcut. A sprite whose mode in attribute 0 is set to semi-transparent uses EVA and EVB whenever the layer immediately behind it is a second target, regardless of `BLDCNT`'s first targets and selected effect. It still needs that second target. Overlapping sprites have already been reduced to one sprite pixel before this stage, so they can't be alpha-blended with each other.

## Fades

Effects 2 and 3 don't need a second layer. They move every first target toward white or toward black by **EVY** sixteenths, which `BLDY` holds:

<Math block tex={String.raw`\begin{aligned} \text{brighter: } I' &= I + \left\lfloor \frac{(31 - I) \cdot \text{EVY}}{16} \right\rfloor \\[0.4em] \text{darker: } I' &= I - \left\lfloor \frac{I \cdot \text{EVY}}{16} \right\rfloor \end{aligned}`} />

Here, <Math tex="I" /> is the original channel and <Math tex="I'" /> the result. The floor applies to the amount added or subtracted. EVY works like EVA and EVB, so values above 16 count as 16 here as well.

That's how the author's name fades in at the end of the *Tales of Phantasia* intro. Once the quote is complete, the game switches window 0 off and sets `WININ` to `0x2800`, which shows BG3 inside window 1 and turns on its effects bit. `BLDCNT` is `0x00ff`: every layer is a first target and the effect is 3, darken. `BLDY` then counts down from 16 to 0 over about 60 frames. Halfway through, at EVY = 8, the white parts of the name are 16 out of 31:

<Math block tex={String.raw`\displaystyle 31 - \left\lfloor \frac{31 \cdot 8}{16} \right\rfloor = 31 - 15 = 16`} />

Only window 1 has its effects bit set, so the quote above the name stays at full brightness the whole time. At the very end, the game turns the windows off and raises `BLDY` to 16 again, which darkens the whole screen to black. Play the windows demo above to the end to see both fades.

A fade doesn't have to use brightness, though. When you start a new game of *The Legend of Zelda: The Minish Cap*, it tells the legend in stained-glass pictures. The narration under each picture fades in with alpha blending instead:

<Math block tex={String.raw`\min\left(31,\ \left\lfloor\frac{0 \cdot 12 + 31 \cdot 9}{16}\right\rfloor\right) = \lfloor 17.4375 \rfloor = 17`} />

The picture itself is a first target as well, so blending would dim it too. Window 0 prevents that: it covers the picture, from y 0 to 95. `WININ` is `0x001f`, which shows every layer inside it but leaves the effects bit clear. `WINOUT` is `0x003f` and has the effects bit set, so the effect only applies to the area below the picture. For the third picture, the game moves window 0 to the left half of the screen and the narration to the right. The same registers keep the effect on the text.

## Mosaic

The last effect doesn't hide or mix a layer, it makes it blockier. When Mario enters a level from the map in *Super Mario World*, the map dissolves into larger and larger blocks:

<figure className="not-prose my-8">
  <img src="/images/gba-bitmap/mario-world-mosaic.gif" alt="The Yoshi's Island map breaking up into ever larger square blocks and getting darker, while Mario and his name tag stay sharp." width="240" height="160" loading="lazy" className="block h-auto w-full" style={{ imageRendering: 'pixelated' }} />
  <figcaption className="mt-2 text-center text-sm text-muted-foreground">The map breaks into larger blocks while Mario and his name tag stay sharp.</figcaption>
</figure>

`MOSAIC` holds 2 block sizes, one for the backgrounds and one for the sprites. Each is a width and a height in pixels, stored minus 1:

<BitLayout label="MOSAIC" fields={[
  { bits: [0, 3], name: 'Background width - 1' },
  { bits: [4, 7], name: 'Background height - 1' },
  { bits: [8, 11], name: 'Sprite width - 1' },
  { bits: [12, 15], name: 'Sprite height - 1' },
]} />

A background only uses them if bit 6 of its `BGxCNT` is set. A sprite only uses them if bit 12 of its attribute 0 is set. For a regular background, the blocks line up with the screen and each one takes the color of its top-left pixel. With a width of 6, for example, pixels 0 to 5 of every line show pixel 0, pixels 6 to 11 show pixel 6 and so on. *Super Mario World* sets the mosaic bit on all of its backgrounds and writes the same size to all 4 fields, from `0x1111` for 2 × 2 blocks to `0xffff` for 16 × 16. Mario and his name tag have their sprite mosaic bits clear, so they stay sharp. The fade routine also subtracts 2 from each palette color's 5-bit channels, stopping at 0. That's why the map gets darker as the blocks grow.

## Putting it all together

We can now put these steps together to render regular backgrounds and sprites:

1. **Mosaic:** For a background with its mosaic bit set, round the pixel's position down to the start of its block before looking it up. Apply the sprite block lookup to enabled sprites as well.
2. **Window region:** The pixel is in window 0 if it's inside it. Failing that, it's in window 1, then in the OBJ window, otherwise outside. That region's byte in `WININ` or `WINOUT` decides which layers it shows and whether effects are allowed. If no window is switched on in `DISPCNT`, everything is allowed.
3. **Layers:** Take the backgrounds that are switched on in `DISPCNT` and allowed in the region, skip the ones that are transparent at this pixel and sort the rest by priority, with the lower BG number first on a tie. The sprite pixel goes in front of every background with the same or a higher priority number. The backdrop comes last.
4. **Effects:** Only the frontmost layer and the one right behind it matter. A semi-transparent sprite in front is alpha-blended with the layer behind it if that's a second target. Otherwise, if the region allows effects and the frontmost layer is a first target, `BLDCNT` decides: alpha blending, if the layer behind is a second target, or brightness.
5. **Output:** Each 5-bit channel is expanded to the 8 bits a modern screen expects.

## Back to the opening frame

With everything from this part, here's how one pixel of the *Shaman King* frame gets its color. The pixel at (223, 111) is on the player character's clothes, in front of the hills:

1. BG0 and BG1 are transparent there.
2. BG2's hills have color (18, 15, 12) and BG3's sky (16, 22, 28). Both have priority 3, so BG2 wins the tie.
3. A sprite pixel with priority 2 is there as well, colored (15, 27, 22). 2 is lower than BG2's 3, so the sprite goes in front.
4. `DISPCNT` is `0x1f40` and has no window switched on, so every layer is visible everywhere.
5. The demo leaves this sprite color unchanged, matching the pixel in the image.

The pixel ends up as (15, 27, 22). So far, we've used scrolling and position changes to move the layers. [Part 3](/posts/gba-graphics-3-affine/) looks at the backgrounds and sprites the GBA can rotate and scale.
